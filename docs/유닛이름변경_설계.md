# 유닛 이름 일괄 변경 rule

대상 : `rules/BatchRename.iLogicVb`

같은 유닛을 새 프로젝트로 다시 내보낼 때 프로젝트 코드만 바꿔서 발주하는
작업을 자동화한다.

```
LIKG-LM2102-FTL02-01  ->  LIKG-LM2602-FTL02-01
          ~~~~                        ~~~~
```

## 원래 하던 방식과 무엇이 다른가

| | 원래 | 이 규칙 |
|---|---|---|
| 이름 입력 | BOM 에서 파일 수만큼 타이핑 | 찾기/바꾸기 한 번 |
| 부품 선택 | 조립도에서 골라 선택 | 없음 (트리 전체) |
| 서브조립도 | 하나씩 들어가서 다시 실행 | 필요 없음 |
| 도면 | 이름이 맞는 것만 | 참조된 것 전부 |
| 결과물 | 사본이 새 폴더에 생김 | 제자리에서 이름이 바뀜 |

새 이름은 옛 이름에서 기계적으로 나온다. 사람이 칠 이유가 없고, 치지 않으면
오타도 없다.

## 서브조립도에 들어갈 필요가 없는 이유

BOM 편집기는 그 조립도 **한 레벨**만 다룬다. 그래서 서브조립도마다 열고 →
BOM 켜고 → 고치고 → 규칙 돌리고를 반복하게 된다. BOM 을 경유하기 때문에
생기는 문제다.

이 규칙은 BOM 을 거치지 않고 `AllReferencedDocuments` 를 쓴다.

```vb
For Each d As Document In oTop.AllReferencedDocuments
```

이 한 줄이 깊이에 상관없이 트리 전체를 평평한 목록으로 돌려준다. 서브조립도는
그 목록의 한 항목일 뿐이라 부품과 똑같이 다룬다. 최상위 조립도 하나에서
한 번 돌리면 끝난다.

## 핵심은 SaveAs 의 두 번째 인자다

```vb
SaveAs(경로, True)    ' 사본 저장. 열려있는 문서는 옛 파일에 그대로 남는다
SaveAs(경로, False)   ' 문서 자신이 새 파일로 옮겨간다
```

`False` 로 두면 인벤터가 **열려있는 모든 상위 문서의 참조를 자동으로 갱신한다.**
조립도든 도면이든 전부.

그래서 순서가 이렇게 된다.

```
1) 최상위 조립도를 연다              - 트리 전체가 메모리에 올라온다
2) 관련 도면을 전부 연다 (비표시)     - 도면도 부품을 참조한 상태가 된다
3) 트리 아래쪽(부품)부터 SaveAs(새이름, False)
4) 도면도 SaveAs(새이름, False)
5) 전부 저장
6) 옛 파일을 _OLD 폴더로 옮긴다
```

**2번의 순서가 중요하다.** 도면을 이름 바꾸기 전에 열어야 한다. 뒤에 열면
도면이 옛 파일을 찾다 실패한다.

### 이 방식으로 없어진 것들

앞선 검토(사본 방식)에서 나왔던 치명 버그가 대부분 원인부터 사라진다.

| 없어짐 | 이유 |
|---|---|
| `ReplaceReference` 재연결 코드 | 인벤터가 알아서 한다 |
| `File.Copy` 후 읽기전용 도면 저장 실패 | 파일을 복사하지 않는다 |
| 어긋난 참조를 안고 도면을 여는 문제 | 참조가 어긋날 일이 없다 |
| 워크스페이스 전체 재스캔 (부품 수만큼) | 폴더의 `.idw` 를 한 번만 훑는다 |
| `Replace` 실패 (패턴 요소) | `Replace` 를 쓰지 않는다 |

## 구매품은 저절로 걸러진다

찾을 문자열(`LM2102`)은 우리가 설계한 가공품 이름에만 들어있다. 구매품은
제조사 품번이라 그 문자열이 없다. 그래서

> **파일이름에 찾을 문자열이 없으면 건드리지 않는다**

이 한 줄이 곧 가공품/구매품 판별기다. 별도 목록이 필요없고, 컨텐츠센터 부품과
라이브러리 부품도 같은 이유로 자동 제외된다.

미리보기 아래쪽에 **"바뀌지 않는 파일"** 목록을 함께 띄운다. 거기 가공품이
섞여 있으면 이름 규칙에서 벗어난 파일이라는 뜻이다. 지금까지는 그것을 알
방법이 없었다.

## 타이틀블록

부품번호 iProperty 를 같은 규칙으로 치환한다. 타이틀블록이 iProperty 연동이므로
도면은 저절로 따라온다. 도면 텍스트를 따로 손대지 않는다.

## 안전장치

- **새 이름이 이미 있으면 그 항목을 막는다.** `_2` 를 붙이지 않는다.
  이 작업에서 `_2` 는 잘못된 번호가 그대로 발주로 나간다는 뜻이다.
- **옛 파일은 지우지 않고 `_OLD_yyMMdd_HHmm` 폴더로 옮긴다.** 되돌릴 유일한 수단.
- 읽기전용 파일은 건드리지 않는다.
- 상관없는 문서가 열려있으면 경고한다. 같은 부품을 쓰고 있으면 그쪽 참조까지
  함께 바뀌기 때문이다.
- 미리보기에서 항목별로 뺄 수 있다.

## Inventor 2026 컴파일 위험을 피한 곳

기존 규칙들이 2026 에서 깨졌던 것과 같은 원인을 미리 피했다. **컴파일 오류는
`Try` 로 막을 수 없기** 때문에 처음부터 이름을 적지 않는 쪽을 택했다.

- **`System.Drawing.Font` 를 직접 적지 않는다** (`SetMonoFont`).
  `System.Drawing` 이 iLogic 참조 목록에 없으면 그 자리에서 컴파일이 깨진다.
  `Font` 속성의 `PropertyType` 으로 타입을 얻어 리플렉션으로 만든다.
  실패해도 기본 글꼴로 나올 뿐이다.
- **`frm.AcceptButton` 대입을 리플렉션으로 넘긴다** (`SetDefaultButtons`).
  `BatchPrint` / `BatchRevisionGeneration` 과 같은 처리.
- **람다와 `AddressOf` 델리게이트를 쓰지 않는다.** 정렬은 명시적 루프로,
  전체선택/해제 버튼은 넣지 않았다. 저장소의 다른 규칙에 전례가 없어
  검증되지 않은 구문을 늘리지 않았다.

## 검증한 것

- **구조** : Sub / Function / Class / Try / For / Do / If 짝 일치 — 통과.
  줄바꿈(`_`) 을 이어붙인 뒤 검사.
- **문자열 따옴표 홀짝** — 통과.
- **프로시저 선언/호출 대조** — 미정의 호출 없음, 미사용 정의 없음.
- COM 객체는 같은 문서라도 다른 래퍼로 넘어올 수 있어 `Is` 비교가 어긋난다.
  문서 비교를 전부 `FullFileName` 기준으로 바꿨다.
- 인벤터가 없는 환경이라 COM 호출은 실제로 돌려보지 못했다.

## 처음 쓸 때 확인할 것

**반드시 시험용 사본 폴더에서 한 번 돌려보고 실제 작업에 쓰세요.**
COM 동작을 검증하지 못했습니다.

- 미리보기의 "바뀌지 않는 파일" 목록에 가공품이 없는지
- 도면 타이틀블록의 부품번호가 실제로 바뀌었는지
- `_OLD` 폴더에 옛 파일이 다 들어갔는지
- 조립도를 다시 열었을 때 참조가 다 살아있는지

## 남은 것

- **폴더 이름은 바꾸지 않는다.** 파일 이름과 부품번호만 바꾼다.
  폴더에도 프로젝트 코드가 들어있다면 폴더는 손으로 바꿔야 한다.
- 도면이 부품과 다른 폴더에 있으면 `DWG_ROOT` 상수에 그 폴더를 적어야 한다.
  비워두면 최상위 조립도가 있는 폴더(하위 포함)를 훑는다.
- **Vault 로 옮긴 뒤에는** Copy Design 이 이 작업을 정식으로 지원한다.
  번호매기기 규칙으로 일괄 치환이 되고, 어느 조립도가 그 부품을 쓰는지도
  Vault 가 추적한다. 서버에서 개인 작업공간으로 통째로 복사해 오는 단계
  자체가 없어진다. 이 규칙은 그 전까지 쓰는 다리다.
